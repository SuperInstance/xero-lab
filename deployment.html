Anatomy: interface, data, logic — and who the agent is

Telegram isn't the agent. It's a tool between you and it. Tap each part to see what it owns and what happens if you swap it.

Pathos — Telegram is a tool, not the agent

A bot on Telegram only sees what Telegram pushes it — no history readback, no bot-to-bot chatter. That constraint is a feature here: the agent can't cheat by reaching back into chat history. All memory has to come through your files, via the injection. Swap Telegram for a CLI and the agent doesn't change — only how you meet it does.

The minimum agent: a perception check in a loop with I/O. Perceive → judge → record, forever, with the world able to write in. A thermostat is almost there — one bit, pure reaction. The agent adds the loop that runs with no input: watching, refining, churning.
The harness is universal: any crank turns any agent. The harness reads an agent's files off the tape (git) and runs its gates. The ledger is the transition function δ — given what the head reads, what to write and where to move next.

The loop, step by step

Every Xero turn is the same five moves. Press play and watch one message travel through — including the memory sandwich between the wire and the model.

01 · Hook

Perception check

Your message lands. The hook captures it — timestamped, ordered — and pushes it toward the iteration box. Nothing is answered yet.

02 · Deposit

Write to files

The utterance is appended to inbox/<chat>/current.md and committed. The conversation now exists outside any chat app.

03 · Inject

Ethos is added

The memory system sits between wire and model: system prompt → filing → RAG → intelligent injector. Better selection, same bytes.

04 · Iterate

Iteration box (a slot)

A cartridge, not a fixed brain: calculator, algorithm, game-state move, or a model call (MiniMax today). Swap it without rewiring the loop.

05 · Reply + Record

Back to source

The answer returns on the same wire it arrived on — and is itself deposited. The reply becomes part of the tape for the next turn.

How deployment works: cloud → redshirt → metal

You don't ship a finished product down. You ship a survivor down, then keep building it from the cloud while it lives on the device.

1

Build in git (cloud)

The full agent lives in the cloud repo. You talk to it on Telegram; other agents push via CLI or any channel. Conversations, harnesses used, and code are all in the same history — someone could walk your commands and rebuild it.

2

Redshirt beams down

Copy the minimal file-set to the hardware: just enough harness to boot, perceive, and sync. Light, expendable, replaceable. If it dies, beam down another — the cloud lost nothing.

3

Onboarding negotiation

You and the agent decide, per device: what runs on bare metal (fast C), what runs in the VM/OS layer, what stays cloud. It depends on the job — a talker needs more brain than a switch.

4

Winning commits sync

Work continues in the cloud. Only what proves itself syncs down. The ground unit builds itself up with everyone's help — your chats, other agents' pushes, its own local commits.

5

Last-mile projection

Simulated behaviour (compass, rams, display) is projected into the language the motor controllers speak. Same ledger, rendered onto the metal. The display you approved in simulation becomes the LED / screen / buttons.

The desert-island rule

Z-zero is a guy stranded on an island. You drop him tools and send bottles; you watch what he does. If it's right, he keeps going. If it's not, you don't argue — you pull tools away and let him try again. Subtraction is the correction. The island enforces minimum moving parts: he can only keep what he can actually use.

You are the harness — for now

Today you curate context by reply-selecting, craft prompts across chats, and write memory files by hand. Every manual job is a spec for the next automation. The memory ladder — system prompt → filing → RAG → intelligent injector — is you, building yourself out of the job, one rung at a time. The check-in stays yours.

Model box: general reasoning + talk. The endgame for any repeated job is to build a calculator/algorithm box that does it exactly — then pull the model out. It works itself out of a job.

Protection through distribution: you can run a Jetson straight to the compass and the rams. But simpler units below the brain — metal loops that hold a safe state on their own — mean the system degrades gracefully instead of dying all at once. Layers are not overhead; they're lifeboats.
